# Languages & Translation

Open Historia is written in English and played in any of fifty languages. Every string the game shows falls into one of three kinds, and each kind is translated differently:

| Kind | Examples | Translated by | Cost to the player |
|---|---|---|---|
| **Interface** | buttons, tabs, labels, hints, errors, the tutorial, stock country names, the built-in scenarios' cards | the **shipped language packs** (`public/lang/<code>.json`) | nothing |
| **Content** | a scenario's and a saved game's name and description, polity names, roles and notes, the scenario's own events, a custom Stats sheet, region names, country names a pack lacks, Community posts | the player's **AI model**, once, then saved to the server's language pack | a few requests the first time a language meets that content |
| **AI writing** | events, chats, the advisor, summaries written during play | nobody: the model writes them in the player's language (`languageDirective`) | nothing extra |

The default prompts' **guidance passages** (the role, the tone, what makes a good event: the parts an author edits in the Prompts tab) ship translated too (`public/lang/prompts/<code>.json`), so the model that runs the world reads its instructions in the player's language wherever the scenario has not written its own. The prompts' technical template (placeholders, output contracts, map rules) stays English, because the game parses what it asks for.

Related pages: [Runtime services](runtime-services.md) · [Prompt-Making Guide](ai-prompts.md) · [Server](server.md) · [Web build](web-build.md)

## Which languages have a pack

`SHIPPED_PACK_LANGUAGES` in `src/runtime/i18n.js` lists them: `ar bn de es fa fr hi id it ja ko nl pl pt ru sv th tr uk ur vi zh`. `src/runtime/languagePacks.test.js` fails if that list and the files in `public/lang/` disagree.

- **With a pack**, the interface is never sent to the AI. A string the pack lacks stays English and is recorded in `window.__ohI18n.missing` (a `Set`, capped at 3,000) for the next pack; `window.__ohI18n.pending` is what is queued for the AI.
- **Without a pack** (the other 27 languages in the picker), the interface goes through the AI as it always did: batched, saved to the server's pack, reused on every device.

## The files

| File | Holds | Made by |
|---|---|---|
| `public/lang/catalog-en.json` | every English interface string, sorted: exact strings and patterns; plus every stock country name, the preset scenarios' card text, and the built-in scenarios' polity names and aliases (`server/seed/*/world.json`) | `scripts/i18n/build-catalog.mjs` |
| `public/lang/<code>.json` | `{ "<English>": "<translation>" }` for the catalog | translation (below) |
| `public/lang/prompts/catalog-en.json` | every guidance passage of the default prompts | `scripts/i18n/build-catalog.mjs` |
| `public/lang/prompts/<code>.json` | `{ "<English passage>": "<translated passage>" }` | translation (below) |
| `server/data/lang/<code>.json` (desktop) / IndexedDB `lang:<code>` (web) | translations the AI made at runtime: content, and the whole interface in a language without a pack | the translator, via `PUT /api/lang/:code` |

`GET /api/lang/:code` (`server/server.js`, and `handleLang` in `src/runtime/web/settingsStore.js` for the web build) returns the saved pack **under** the shipped one: the shipped entry wins, because a saved entry for a string the pack now covers is an older AI translation. `PUT` does not save a string the shipped pack already has.

### Patterns

A string built around a value is a **pattern**: the value is a slot in double braces, named after the expression it came from.

```
"Found {{count}} regions"              → "{{count}} Regionen gefunden"
"{{name}} declared war on {{target}}"  → "{{target}} wurde von {{name}} der Krieg erklärt"
```

A translation keeps every slot and may move it. Plain interface text never contains `{{`, so a key with a slot is a pattern. A choice of strings is expanded into each variant, never a suffix slot: `` `${n} game${n === 1 ? "" : "s"}` `` gives `"{{n}} game"` and `"{{n}} games"`.

## How the game applies a pack — `translator.js` + `phraseBook.js`

`startTranslator()` (called from `src/main.jsx`) runs in native mode for English ("Modes, tiers and the first language" below). For every other language it sets `<html lang>` (and `direction: rtl` for ar/fa/ur/he), starts loading the prompts' passages (`loadPromptTranslations`), reads this device's cache, fetches `/api/lang/:code`, waits for the startup screen to go, then walks the DOM and watches it with a `MutationObserver`.

**Lookup** (`createPhraseBook()` in `src/runtime/phraseBook.js`, pure and tested in `phraseBook.test.js`):

1. the exact string, then the string with its whitespace collapsed;
2. a **date**: the game writes its dates in English ("Jan 1, 2016", "1 March 218 BC", "2016-01-08", from `formatGameDateReadable` in `gameDates.js` and dayjs), and the same functions write the dates the AI reads, so they stay English at the source. `createDateLocalizer` (`src/runtime/localDates.js`) recognizes a string that is exactly one of those shapes and writes it the player's way with `Intl` ("1. Jan. 2016", "2016年1月1日", "1. März 218 v. Chr."), always in the Gregorian calendar and with Latin digits;
3. the patterns, most literal text first: the slots capture the values, each value is itself looked up, exactly or as a date (so `"Edit {{label}}"` over "Edit Borders" reads "Grenzen bearbeiten"), and the translation is filled in;
4. a **list** joined with " / ", " · ", " • " or " | " ("Modern Day Session / Japan / 2016-01-01"), which no pattern holds because it has no words of its own: each part is looked up by itself, and the list changes only when some part is known. Dashes are not separators, since prose uses them.

Two guards keep a short pattern from rewriting prose that merely starts with its words (an English reply in a chat set to another language, say): a **weak** pattern (fewer than 8 letters of its own, like `"Our {{label}}"`) accepts at most 4 words of value, and no value that mixes words and numbers unless the book knows it ("Found 12" before `"{{value}} regions"` is the start of another sentence; "Jan 1, 2016" is a date); and a value never spans two sentences unless the pattern has 16 or more letters of its own. Two slots with nothing between them are never compiled (they cannot be told apart).

**The DOM:**

- A text node is looked up by its English. The translator remembers, per node, the English it last saw and what it wrote (`nodeRecords`), so its own writes are never mistaken for source text and React's next write (new English) is translated again.
- **Runs.** React renders `<p>Found {count} regions</p>` as three text nodes. A parent whose children are all text nodes is read as one string; when the pack knows it, the whole translation goes in the first node and the others are emptied (they keep their English, so React's next update to any of them re-composes the sentence). When the pack does not know the whole, each piece is looked up on its own.
- **Attributes:** `title`, `placeholder`, `aria-label`, `aria-description`, `alt`, observed as they change; and `document.title`.
- **Skipped:** `script, style, noscript, input, textarea, [contenteditable], [data-no-translate]` (an input's own `placeholder` and `title` are still translated).

**Precedence:** the server's pack (shipped over saved) is laid over this device's cache (`localStorage["i18n_v2_<code>"]`), so a stale local translation never hides the pack's. The cache holds only what the AI translated on this device and the server does not have yet. The pre-pack caches (`i18n_cache_*`) are removed on boot; what they held that the server lacked is sent to it first.

**Map labels** are not DOM: `translateLabel(name)` (used by `countryLabels.js` and `Nations.jsx`) looks the name up and queues it as content when unknown; `"i18n:updated"` tells the label builders to rebuild when translations arrive. The country labels of a scenario's own map are built in the political worker from those names, and two labels that read alike fall back to their owners' names; that comparison (`labelFoldKey` in `Nations.jsx`) keeps letters of every script, since a fold to a-z made every Chinese or Arabic name the same empty key and put every label back in English. City names on the map are not translated.

## Content

Content is whatever a scenario's author or a player made. It is gathered up front, so it is translated in a few big requests instead of one panel at a time:

- **At boot and on every switch of save** (`oh:active-game-changed`), `collectContentStrings()` queues: scenario and game cards (`/api/scenarios`, `/api/games`), country names the pack lacks, every polity's name, aliases, role, note and map labels (`world.polityOverrides`), the scenario's own events (those whose `source` is `"scenario"`; the AI's events are already in the player's language), a custom Stats sheet's section and stat labels, descriptions and units, Community posts, and last (the big set) region names.
- **As it is written:** `library.js` calls `enqueueContentStrings(payload)` when a scenario or game is created or saved; `gameState.js` calls it for `polityOverrides` on every world write and `enqueueEventStrings(events)` on every event-log write; `communityHub.jsx` calls `enqueueStrings` for fetched posts.

Anything already known is never queued. The queue is sent one request at a time, up to 240 strings or 6,000 characters a request (`planTranslationBatch`; `translatorBatching.test.js` pins the sizes), halving on a failure and backing off for a minute after three. Results are saved to the server's pack (`PUT /api/lang/:code`), so each string is paid for once, on every device. The requests show as "translation" in Settings → AI, "Used today, by task".

## The prompts

`src/runtime/promptTranslations.js` holds the loaded passages. `localizedGuidanceDefaults()` in `src/Game/AI/gameplayPrompts.js` is the default guidance tree with every passage the pack translates swapped in (memoized by `promptTranslationsVersion()`), and:

- `normalizePromptPack()` composes each prompt from its English template with the **localized defaults under the author's own passages** (`localizedPassages`). An author's passage is theirs, in whatever language they wrote it.
- `normalizePromptGuidance()` drops an edit identical to the localized default, as it drops one identical to the English default (`withoutLocalizedDefaults`), so opening and saving the Prompts tab in German never pins German wording into a scenario other players read.
- The Prompts tab (`PromptSectionEditor` in `libraryBar.jsx`) shows the localized defaults and re-renders when they load.
- `ensurePromptsLoaded()` in `src/Game/AI/main.jsx` keys its cache on the passages' version, so prompts composed before the passages arrived are recomposed.
- Exports and transfers (`materializePackGuidance`) use the English defaults.

The passages are keyed by their English text: a passage whose wording changes simply falls back to English until the packs are regenerated, and a branch whose prompts differ finds only the passages it shares.

## Writing interface code that translates well

The catalog is read out of the source (`scripts/i18n/extractStrings.mjs`), so the way a string is written decides whether a language can translate it:

- **Keep a sentence in one template or one run of text.** `` `${count} regions found` `` or `<p>Found {count} regions</p>` is one pattern a language can reorder. A sentence split around an element (`Found <b>{count}</b> regions`) becomes pieces ("Found", "regions") translated separately.
- **Plurals and variants as whole words:** `` {n === 1 ? "event" : "events"} `` or `` event{n === 1 ? "" : "s"} `` both expand into both variants. Never build a word from pieces a language cannot reorder.
- **Names, codes, numbers and anything the player typed** go in an element marked `data-no-translate`, so they are neither looked up nor mistaken for interface.
- Text-bearing props are read from JSX (`label`, `title`, `hint`, `description`, `placeholder` and the rest of `DISPLAY_KEYS`), from registries in the directories the extractor reads (`src/runtime`, `src/Game/GameUI`, `src/Game/Selection`, `src/Game/Map`, `src/Editor`), and from status setters (`setStatus(...)`, `STATUS_CALLS`). A camelCase key ending in `Label` (`mappedLabel`, `centerSubLabel`) counts too, and its value may be a single lowercase word ("landscape"), which elsewhere would read as an id.
- **A screen shows what it catches.** Every `.jsx` file's thrown and returned prose is read (`throw new Error("Give the group a name.")`), because its screen puts `error.message` in front of the player.
- **Name a constant for what it holds.** Every string in an `UPPER_SNAKE` constant ending in `_LABEL(S)`, `_HINT(S)`, `_INTRO`, `_NOTE(S)`, `_TEXT(S)`, `_MESSAGE(S)`, `_TITLE(S)`, `_DESCRIPTION(S)`, `_BLURB(S)`, `_CAPTION(S)`, `_TOOLTIP(S)` or `_PLACEHOLDER(S)` is read as display text (`STRUCTURED_MODE_LABELS = { auto: "Automatic (recommended)" }`). A constant so named but written for the model goes in `MODEL_CONSTANTS` in the extractor.
- `src/Game/AI/*.js` is prompts and parsers, and is not read, except the registries behind Settings → AI and the Prompts tab (`JS_REGISTRY_FILES`) and the modules whose messages the player reads (`MESSAGE_FILES`: the provider failures, the Fallback list, the context window, the request budget), whose returned and thrown prose is read. The institutions' modules are message modules too (`institutionLifecycle(Core)`, `institutionalGovernance`, `institutionalChannels`, `institutionAuthoring`, `politicalWorldCapability`, and the advisor's and Game Master's institution helpers): what they refuse with shows in the Institutions tab, and the events and channel lines they write are read in the log. A new module of player-facing messages belongs in that list.
- **Write an event or a log line as one sentence per case**, not a sentence assembled from a verb looked up in a table (`${subject} ${actionLabel} ${name}`): a language can translate `"{{subject}} Joins {{name}}"`, never `"{{subject}} {{actionLabel}} {{name}}"`. `lifecycleEventTitle` and `outcomeEventDescription` are the pattern.

## Regenerating the packs

1. **Build the catalogs.** One catalog serves every branch: pass the other branches' trees and it is their union, so the same packs ship everywhere.

   ```
   git archive origin/beta src scripts/presets | tar -x -C ../tree-beta
   git archive origin/main src scripts/presets | tar -x -C ../tree-main
   node scripts/i18n/build-catalog.mjs --also ../tree-beta --also ../tree-main
   ```

2. **Translate what is new.** With an OpenAI-compatible endpoint (the key is read from the environment and never written anywhere):

   ```
   OH_LLM_BASE_URL=… OH_LLM_KEY=… OH_LLM_MODEL=… node scripts/generate-lang-packs.mjs --all
   ```

   It is incremental (only strings a pack lacks are sent), drops entries the catalog no longer has, rejects a translation that loses a placeholder, and does the prompt passages too, one per request. `--lang de,fr` for some languages, `--dry-run` to count, `--force` to redo everything.

3. **Check.** `node --test src/runtime/languagePacks.test.js`: every pack on disk is listed in `SHIPPED_PACK_LANGUAGES` and back, every placeholder survived, and each pack covers at least 90% of its catalog.

To add a language: add its code to `SHIPPED_PACK_LANGUAGES` and to `LANGUAGES` in `generate-lang-packs.mjs`, then run step 2 for it.

## The native Swedish catalog (Attainder)

The character and dynasty system on top of the upstream game is written in Swedish. The engine under `server/characters/` builds log titles, story text, refusals and labels. The components under `src/Game/Characters/`, `src/Game/DynastyStartCard.jsx` and `src/Game/HistoricalStartPicker.jsx` hold Swedish JSX. A few files under `src/runtime/`, `server/historical*.js` and the package builders under `server/seed/historical/` hold more. None of it is in `catalog-en.json`.

An English mode translates this text at display time with the same phrase book, keyed by the **Swedish** source string. `public/lang/attainder/catalog-sv.json` lists those keys:

```json
{ "schema": "attainder-native-catalog-v1", "sourceLocale": "sv", "entries": ["Avbryt", "Riket går i krig vid {{name}}s sida"] }
```

`entries` is sorted and unique. Each key is trimmed and its whitespace runs are single spaces, as the phrase book matches them. A string built around values is a pattern with `{{slots}}`, and a slot that is a choice of strings is one entry per variant, as in the English catalog. Three things differ from it:

- Two interpolations with nothing between them become one slot, because `compilePattern` refuses adjacent slots: `` `${first}${last} går i krig` `` gives `"{{first_last}} går i krig"`.
- A role in single braces is a slot. The event chains write `"{steward} frågar …"` and `render` in `server/characters/eventChains.js` fills in the name, so the entry is `"{{steward}} frågar …"`.
- A template with no letters outside its slots (`` `${name}: ${label}` ``) gives no entry. The phrase book cannot compile one.
- A template keeps up to 64 variants, where the English catalog keeps 8 (`withVariantLimit` in `extractStrings.mjs`). A template that reaches 64 stops the build.

### The script

| Command | Does |
|---|---|
| `node scripts/i18n/build-native-catalog.mjs` | reads the source and writes `public/lang/attainder/catalog-sv.json` |
| `node scripts/i18n/build-native-catalog.mjs --check` | writes nothing and exits 1 when the committed catalog differs from a fresh extraction |
| `node scripts/i18n/build-native-catalog.mjs --context <file>` | also writes the translator context to `<file>`, which is not committed |

The context file lists where each entry comes from: `[{ entry, kind, refs: [{ file, line, enclosingFunction, role }] }]`. `kind` is `string`, `pattern` or `jsx`. `role` is the extractor's best reading of how the text reaches the player: `ui` (a component renders it), `label` (a value in a label map), `log` (the log, memories and stories), `refusal` (an error or a reason the player reads), `seed` (a package builder) or `other`. A translator needs it to choose the English for a short word such as "Val" or "Grepp".

### What the extractor takes

`scripts/i18n/extractNativeStrings.mjs` parses every non-test `.js`, `.jsx` and `.mjs` file under `server/` and `src/`, except `node_modules`, directories named `generated` and `server/fixtures/`. It reuses `shapeOf` and `cleanJsxText` from `extractStrings.mjs`. Three rules decide what is Swedish:

1. **Detected.** The text holds å, ä or ö, or a Swedish function word as a whole word (`SWEDISH_WORDS`) and no English one. A word that English shares ("under", "en") counts only when the text reads like prose or sits in a Swedish file.
2. **Sibling.** A label without those markers ("Krig", "Mat", "Stark") is taken when it sits beside clearly Swedish text: in the same list or map of strings, or in the same field of another row of a table. A row may be built by a call, and its fields are then the argument positions: `band(35, 'osannolik')` beside `band(65, 'osäker')`. A key is the same field wherever it stands in the file, for a value that reads like prose: `rulerOfficeName: 'Kejsare'` beside `rulerOfficeName: 'Påve'` in another constant. The value of a key or constant named as Swedish (`nameSv`, `TRIBE_NAMES_SV`) is taken too.
3. **Swedish file.** In a file where clearly Swedish text is at least half as common as other text, JSX text and text attributes are taken ("Skicka", "Avbryt"), and so are a string that reads like prose ("Ogiltigt val.", `` `${name} friges` ``), the other branch of a ternary with a Swedish branch, the other returns of a function with a Swedish return (`serviceTier`), and the strings of a list or map in a constant named as labels (`LOYALTY_LABELS`). The rows of a table in such a constant (`[['intrigue', 'Intrig'], …]`) are left to the sibling rule.

The words and the letter test are the translator's: the extractor imports `SWEDISH_WORDS` and `hasSwedishLetter` from `src/runtime/swedishText.js`, and adds six words that list leaves out as shared with English (`den`, `till`, `en`, `sin`, `under` as weak markers, `finns` in full). Its English veto, its prose test and the sibling and file rules come on top.

Text in a technical position is never an entry: a comparison, an object key, the argument of `includes` or `split`, a `className`, a `console` call.

### Exclusions

`scripts/i18n/native-catalog-exclusions.json` names every Swedish-looking literal that is not an entry, as `{ "file", "text", "reason" }`. `reason` is `developer-only`, `technical`, `non-display`, `uncompilable-template` or `not-swedish`: English or a code that a Swedish function word also spells, such as "Under construction". For a template, `text` is the template as written, with its `${…}`.

The script fails when a Swedish-looking literal is outside the catalog and the file does not name it, when an entry of the file names nothing, and when a pattern does not compile. A new Swedish string therefore lands in the catalog or stops the build. A literal the file names is never taken, which is how English that the first rule would take is kept out. English without any Swedish marker that the third rule takes with its Swedish file is named the same way: `Politics`, the upstream tag that `characterWorld.js` stamps on its event cards.

## Swedish source text: the native pack

Attainder's character system and historical packages are written in Swedish. In English mode the translator holds a second phrase book keyed by the Swedish, loaded from the native pack. The design is `docs/superpowers/specs/2026-11-11-bilingual-runtime-design.md`.

### The data files

All of them sit in `public/lang/attainder/`, which both builds serve as static files under `<base>lang/attainder/`.

| File | Holds | Made by |
|---|---|---|
| `historical-en.json` | `{ "<Swedish>": "<English>" }`: the pairs of `server/seed/historical/locales/en.json` whose two sides differ, keys sorted | `scripts/i18n/build-historical-pairs.mjs` |
| `historical-sv.json` | `{ "<English>": "<Swedish>" }`: the same for `locales/sv.json` (source locators and institutions), for the Swedish book | `scripts/i18n/build-historical-pairs.mjs` |
| `catalog-packages-sv.json` | `{ schema: "attainder-package-catalog-v1", sourceLocale: "sv", entries: [...] }`: each unique Swedish display string of the four built packages that `historical-en.json` leaves untranslated | `scripts/i18n/build-package-catalog.mjs` |
| `packages-en.json` | `{ "<Swedish>": "<English>" }` for `catalog-packages-sv.json` | translation |
| `en.json` | `{ "<Swedish>": "<English>" }` for the Swedish text in code | translation |

`mergeNativePack` (`src/runtime/nativePack.js`) merges the three English files into one object: `en.json` wins over `packages-en.json`, which wins over `historical-en.json`. `loadNativePack(fetchJson)` fetches them together. A file that fails to load costs its own entries and one `console.warn`.

### The scripts

Each takes `--check`, which writes nothing and exits non-zero when the repository is out of date.

- `node scripts/i18n/build-historical-pairs.mjs` writes both pair files. The game looks a text up without knowing its record, so one source text gets one translation. The build stops and lists each source text the sidecar translates in two ways, counting "leave it as it is" as a translation. `scripts/i18n/historical-pair-rulings.json` names the translation to keep per sidecar (`en`, `sv`) and records the reason under `reasons`.
- `node scripts/check-locale-sidecars.mjs` reads the field each sidecar entry names (`eventId` or `sourceId` with `fieldPath`, or `jsonPointer`) and compares the SHA-256 of that string with `textSha256`, and the string with the source text the entry stores. It prints each mismatch with its id.
- `node scripts/i18n/build-package-catalog.mjs` reads `server/seed/historical/<package>/scenario.json` for the four packages, collects each text under a key ending in `Sv` (map geometry skipped) and writes the strings a native book of `historical-en.json` cannot translate. Run it after the pairs script. `--context <file>` also writes, per entry, its packages and first three JSON paths for the translator. The first run creates `packages-en.json` and `en.json` as `{}`.

- `node scripts/i18n/check-native-pack.mjs` counts `en.json` against `catalog-sv.json` and prints `{ total, translated, missing, slotErrors, empty, unknownKeys }`. `nativePackReport({ catalog, pack })` lists the catalog entries without a translation, the empty ones, the translations whose `{{slot}}` names differ from their entry's (each name as often as the entry writes it, in any order), and the keys of `en.json` that are no catalog entry. Here `--check` fails when any of the four lists has an item, which it does until the translation slice is in.

A rebuilt package with new text fails `build-package-catalog.mjs --check` until someone rebuilds the catalog and translates the new entries.

### The native options of the phrase book

`createPhraseBook({ native: true })` adds four lookups. The books keyed by English are created without the option and translate as before.

1. **Values by pattern.** A slot's value is looked up with the whole book, patterns included, two levels down: `Spelbara riken: {{list}}` over `Frankerriket och Tangriket` reads `Playable realms: Frankish kingdom and Tang Empire` when the book has `{{name}} och {{other}}`.
2. **Comma lists.** A value or a whole string of 2 to 15 items joined by `", "` is translated item by item when the book has an exact entry for each item. One unknown item leaves the string as it is.
3. **The final period.** A string the book lacks that ends in one period is looked up without it, exactly and then by pattern, and gets the period back. The package builders close a dossier sentence with a period, and `{{x}}.` cannot be a pattern.
4. **A lowercased label.** The engine writes a label into a sentence with `label.toLowerCase()`: `avslöjats för mord`, from the label `Mord`. A value or a whole string that starts in lower case and is otherwise unknown is looked up with a capital, among the entries, and the answer gets its first letter lowered: `murder`. The answer keeps its capital when its second letter is a capital too (`HIV`) and when it opens with the same word as the Swedish label, a name both languages write alike (`Silla`). An entry for the lowercase text is looked up first and settles any other case, such as an English word that keeps its capital (`Christian`).

`book.translate(text, { strongOnly: true })` is the tier for text outside the views written in the book's language. Exact entries answer, and patterns with at least eight letters of their own (`STRONG_LETTERS`). A list or a missing period resolves through exact entries alone, and the date rule applies to a value inside such a pattern but never to a whole string. The lowercased label answers for a value inside such a pattern, never for a whole string. A weak pattern such as `{{name}} dog {{date}}` therefore leaves `Hot dog stand` alone. The book remembers the answers of the two tiers apart.

## Modes, tiers and the first language

`translatorMode(language)` in `src/runtime/translatorMode.js` names what `startTranslator()` does. The module holds each decision that depends on the mode as a pure function, so the tests ask them without a DOM.

| Mode | Language | Book | A string the book lacks |
|---|---|---|---|
| `pack` | every language except English | the language's pack, keyed by English, with the date rule | with a shipped pack it is listed in `missing`, unless `looksSwedish` says it is the court's own text; without one it is queued for the AI model, unless the language is Swedish and `looksSwedish` says the string is too |
| `native` | English (`en`) | the native book, keyed by Swedish: `createPhraseBook({ native: true })`, no date rule | inside a Swedish-native view it is listed in `missing`, whatever it looks like; outside one it is listed when `looksSwedish`, otherwise left as it is |
| `off` | none | none | left as it is |

**Native mode** fetches the three files of the native pack and nothing else. It reads no `localStorage` cache, no `/api/lang/en` and no prompt passages, collects no content, sends no model request and no `PUT`. `translateLabel` returns the book's entry for a map label and queues nothing. `nativeReading(text)` returns the whole book's reading of a string a Swedish-native view searches without rendering it, and lists nothing: the start picker adds it to each row's search text, so `Roman` finds `Romarriket`, and builds its rows again on `i18n:updated`. `enqueueStrings`, `enqueueContentStrings` and `enqueueEventStrings` return at once.

**Pack mode** works as the sections above describe, with three additions. In Swedish mode a string that `looksSwedish` is never queued for the model (`mayQueueForModel(mode, text, language)`): the court and package text is Swedish, and the model would be asked to put it "from English" into Swedish. The check is made in Swedish only. The detector reads a name with ä or ö (`Kärnten`, `Bingöl`) and English with a shared word (`kung fu`, `ska`) as Swedish, and in German or Turkish such content has to reach the model like any other; Swedish text that reaches it there is translated as before the modes. With a shipped pack a string that `looksSwedish` is left off the `missing` list in every language: it is no gap in a pack keyed by English. In Swedish mode the book also takes `historical-sv.json` (`loadSwedishHistoricalPack`), laid under the server's pack, so a research pair never replaces an entry the pack has.

`looksSwedish(text)` in `src/runtime/swedishText.js` is true for text with å, ä or ö, and for text with a word of `SWEDISH_WORDS` between non-letters. A word counts in lower case anywhere, and with a capital only as the first word of the text. Function words that English shares (`en`, `den`, `sin`, `till`, `under`, `finns`) are left off the list. Over `catalog-en.json` the rule matches one entry, the place name `Åland`, and no entry through a word. It does not recognise 583 of the 3,169 entries of `catalog-sv.json` (`Till:`, `den Store`, `Krig`), which is why native mode does not ask it inside a Swedish-native view; `swedishText.test.js` pins the number.

`isTranslatable` counts two adjacent letters of any script as a word, so `Mål` and `Hög` are looked up. Only text with two adjacent Latin letters is queued for a model or listed as missing from a pack, so an event the model wrote in Chinese is left alone as before.

`window.__ohI18n` is `{ language, mode, packed, pending, missing, rescan }` in both modes, and `<html lang>` is set in both. A second `startTranslator()` call while the first is in effect does nothing; a call after `stopTranslator()` starts again.

### The two tiers

Native mode scans the whole page, because Swedish court text also reaches upstream views such as the event log.

| Where | Attribute | What applies |
|---|---|---|
| inside a Swedish-native view | `data-native-text` on the view's root | the whole native book: `book.translate(text)` |
| the title and description of a character-system event in an upstream view | `data-native-text` on those two elements, from `nativeEventProps(event)` | the whole native book |
| everywhere else, and `document.title` | none | exact entries and strong patterns: `book.translate(text, { strongOnly: true })` |
| text the model or the player wrote | `data-no-translate` on its container | nothing, in every mode |

A translated attribute (`title`, `placeholder`, `aria-label`, `aria-description`, `alt`) takes the tier of its element. `data-native-text` has no effect in pack mode.

The character system writes its public events into the world's event stream with `source: "character-system"` (`characterTransitionEvents`), and most of their titles are weak patterns (`{{name}} föds`). `nativeEventProps(event)` in `translatorMode.js` gives the marker for such an event and nothing for any other. The Events panel, the stop-the-round question, the country panel and the Game Master timeline spread it on the elements that hold the event's title and description; the date, the tags and the buttons beside them stay in the strong tier.

`translateInTier(book, text, tier)` is the lookup the translator makes. In the strong tier it skips the entries of `SHARED_WITH_INTERFACE`: Swedish keys that the English interface also writes with another meaning. Today that is `stat`, the Swedish for a state and the interface's word for a statistic. The interface catalog is not loaded at run time, so the list is written out, and `nativePackData.test.js` fails when it differs from the real overlap of the catalogs.

### The first language

`INITIAL_LANGUAGE` (`sv`) is what an install reads before a language is stored. `DEFAULT_LANGUAGE` (`en`) still names the language of the upstream source text. Four functions of `src/runtime/i18n.js` carry the rule:

- `getStoredLanguage()` returns the stored code, or `sv`.
- `writeLocalLanguage(code)` stores every code, `en` included, and returns whether the value reads back.
- `setStoredLanguage(code)` sends the server the code it was given.
- `syncLanguageFromServer()` adopts the server's `language` only when it is a code in `LANGUAGES`. It returns `true`, which reloads the page, only when the language this device reads changed and the new value reads back.

| Install | First boot |
|---|---|
| nothing stored on the device or the server | Swedish, no reload |
| the server has `language: "en"`, the device has nothing | starts in Swedish, stores `en`, reloads once into English |
| `localStorage` is blocked | Swedish on every boot, no reload; a choice in Options reaches the server and not this device |
